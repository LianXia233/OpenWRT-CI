# Hiveton H5000M 自用配置（NetMonitor 网络监控 + Taygedo 签到 + MT5700 方案）
#
# ⚠️ 本配置为【个人自用】配置：
#   - 仅服务作者自有的 H5000M 设备；
#   - 产物在 Releases 中单独归组「自用」（Release 标题 / Tag 保持中文，
#     形如 自用-<YY.MM.DD>；固件名模组段为 ASCII 的 SelfUse），
#     不进入 MT5700 / MT5700M / FM350 / NetWiz / BASE
#     等其他任何分类。
#
# 在现有 MT5700 方案基础上新增两个 LianXia233 插件：
#   - luci-app-netmonitor —— 网络延迟 / 连通性实时监控
#     （https://github.com/LianXia233/luci-app-netmonitor）
#   - luci-app-taygedo    —— 塔吉多（幻塔 / 异环）每日自动签到
#     （https://github.com/LianXia233/taygedo-CI）
#
# MT 插件层刻意不写在本文件中：由调用方传入 MT_MODE=MT5700，由
# Scripts/ApplyMTMode.sh 在 Settings.sh 之后叠加 Config/MT5700.txt 并执行
# 互斥保护（MT5700M 侧包会被强制禁用）。
#
# 定时工作流（H5000M-NETMONITOR-AUTO）已绑定 MT_MODE=MT5700；手动触发
# WRT-BUILD 时必须把 MT Mode 下拉同步选为 MT5700，若留空 ApplyMTMode
# 空模式会禁用全部 MT 包，产物将缺少 MT5700 模组功能，名不副实。
#
# 命名保留 "H5000M-WIFI-YES" 子串以继承按机型名匹配的既有逻辑
#（WRT-CORE 中 AP3000M 专属步骤靠 contains 命中，本配置为 H5000M 不受影响）。
# 设备平台
CONFIG_TARGET_mediatek=y
CONFIG_TARGET_mediatek_filogic=y

# 仅编译 Hiveton H5000M
CONFIG_TARGET_MULTI_PROFILE=n
CONFIG_TARGET_ALL_PROFILES=n
CONFIG_TARGET_DEVICE_mediatek_filogic_DEVICE_hiveton_h5000m=y

# 内核调整
CONFIG_PACKAGE_kmod-cryptodev=y
CONFIG_PACKAGE_kmod-tls=y

# H5000M 专用硬件
CONFIG_PACKAGE_luci-app-h5000m-fancontrol=y

# ===== luci-app-netmonitor：网络质量监控（自用）=====
#
# 包来源：https://github.com/LianXia233/luci-app-netmonitor（分支 main，版本 1.2.1）
# 构成：procd 常驻守护（netmon-daemon.sh）+ ucode RPC（luci.netmonitor）+
#       LuCI JS 前端，LUCI_PKGARCH=all（纯文本架构，无 Rust 编译）。
# 其 Makefile 走 feeds/luci/luci.mk 编译框架，源码由
# Scripts/Packages-NetMonitor.sh 在 make defconfig 之前就位。
#
# Makefile 的 LUCI_DEPENDS 为 +luci-base +luci-mod-status +ucode-mod-fs
# +ucode-mod-uci +ucode-mod-ubus +ucode-mod-uloop，其中 luci-base 已在
# Config/GENERAL.txt 选中；其余逐项显式选中，避免依赖链变动时静默缺包
#（做法与 NetWiz 配置一致：依赖只靠 DEPENDS 隐式解析时，一旦上游调整
# 打包或某依赖在别的配置层被置 =n，make defconfig 后会缺功能组件）。
CONFIG_PACKAGE_luci-app-netmonitor=y
CONFIG_PACKAGE_luci-i18n-netmonitor-zh-cn=y
CONFIG_PACKAGE_luci-mod-status=y
CONFIG_PACKAGE_ucode-mod-fs=y
CONFIG_PACKAGE_ucode-mod-uci=y
CONFIG_PACKAGE_ucode-mod-ubus=y
CONFIG_PACKAGE_ucode-mod-uloop=y

# ===== luci-app-taygedo：塔吉多自动签到（自用）=====
#
# 包来源：https://github.com/LianXia233/taygedo-CI（分支 main）。
# 构成：LuCI JS 前端（服务 → 塔吉多签到）+ Rust 后端 /usr/bin/taygedo-rs。
#
# 后端**从源码交叉编译**（不经 OpenWrt 的 lang/rust feed，避免连 rustc 一起
# 编 1.5~3 小时）：
#   1. defconfig 之前，Scripts/Packages-Taygedo.sh 把包与 Rust 工程放进
#      package/luci-app-taygedo/（Rust 工程在 rust/）；
#   2. defconfig 之后，Scripts/Build-Taygedo.sh 用宿主机 rustup +
#      OpenWrt staging_dir 的 aarch64-openwrt-linux-musl-gcc 编译
#      `--no-default-features --features openwrt`，产物落到包目录 local/。
#
# 导入由配置文件驱动（本文件写了下面这行就会导入，与机型名无关）。
# 包 Makefile 见到 local/taygedo-rs 即跳过 GitHub Release 下载；只有源码
# 编译不可用时才回退预编译资产（TAYGEDO_PREBUILT=1）。
#
# DEPENDS: +ca-bundle +luci-base +curl（luci-base 已在 GENERAL.txt 选中；
# ca-bundle 在 GENERAL.txt 中被注释，故此处显式选中）。
CONFIG_PACKAGE_luci-app-taygedo=y
CONFIG_PACKAGE_ca-bundle=y

# ===== luci-app-honk：eBPF 透明代理（自用）=====
#
# 包来源：https://github.com/QiuSimons/luci-app-honk
#   - honk            —— honk-core（dae 兼容的 eBPF 透明代理）+ init.d +
#                        /etc/honk 默认配置；
#   - luci-app-honk   —— LuCI 页面 + rpcd/ucode 接口 + Doona 静态面板。
#
# 为什么从源码编译：上游 Release 只提供 aarch64_generic 的 ipk/apk；
# H5000M 实机是 Cortex-A53，OpenWrt 给它打的包架构是 aarch64_cortex-a53，
# apk 会直接拒绝 aarch64_generic 的包。因此不在取包阶段下载预编译 core，
# 改为让 honk 的 Build/Compile 调用包内 build_honk_core.sh 源码编译；
# 产物架构跟随 target，最终 honk apk 是 aarch64_cortex-a53，实机可正常安装。
# 源码编译需要 Rust(nightly/rust-src) + Zig + bpf-linker + clang/llvm；
# Scripts/Packages-Honk.sh 在 defconfig 前装好工具链并写入 GITHUB_PATH，
# 构建时间预计增加 15~30 分钟，仍远低于 GitHub 6 小时上限。
# 注：上游 Makefile 的可选依赖 +HONK_USE_VMLINUX_BTF:vmlinux-btf 在目标
# 源码树没有对应包，make defconfig 会打印一条 warning；本配置固定选
# 内核 BTF（CONFIG_HONK_USE_KERNEL_BTF=y），不会引用该可选包。
#
# 导入由配置文件驱动：workflow 只要看到下面这行
# CONFIG_PACKAGE_luci-app-honk=y 就调用 Scripts/Packages-Honk.sh，
# 与机型名无关；不写就不导入，其他配置零影响。
#
# 依赖逐项显式选中（理由与 NetWiz / taygedo 段一致：依赖只靠 DEPENDS 隐式
# 解析时，一旦上游调整打包、或某依赖在别的配置层被置 =n，defconfig 后会
# 静默缺组件，而固件编译仍然全绿）：
#   - 内核：kmod-sched-core / kmod-sched-bpf / kmod-veth / kmod-nft-queue；
#   - 数据：v2ray-geoip + v2ray-geosite（落到 /usr/share/v2ray，honk 的
#           geoip:/geosite: 规则要靠这两份 .dat 才能解析）；
#   - LuCI：rpcd-mod-ucode（honk.uc 的 RPC 接口）、unzip（Doona 面板解包）；
#   - 工具：jsonfilter（honk.init 用 ubus 状态解析 DNS 时调用，
#           LuCI 自身不保证带上，显式选中以免 DNS 劫持退回硬编码）。
#   ca-bundle 已在上方 taygedo 段选中，不重复声明。
#   注：honk.init 其余只用 ip / ubus / mount（基础镜像已有），
#   不需要 jq / nsenter / tc-full；上游 Makefile 也未声明它们。
#
# eBPF CO-RE 的硬前提：honk-core 启动时要读 /sys/kernel/btf/vmlinux。
# ImmortalWrt 的 filogic 内核默认不带 BTF，且 Config-kernel.in 里
# KERNEL_DEBUG_INFO_REDUCED 默认 y（与 BTF 互斥），所以下面三行必须一起写：
#   - DEBUG_INFO 打开 DWARF；
#   - DEBUG_INFO_BTF 让 pahole 生成 BTF；
#   - 显式关掉 DEBUG_INFO_REDUCED，否则 defconfig 会把 BTF 选项静默丢掉。
# 代价：构建会多编 tools/dwarves（pahole），build_dir 也会变大；但这是
# honk 在本机能跑的硬前提，不能省。workflow 的校验步骤会在编译前检查这三项。
CONFIG_PACKAGE_honk=y
CONFIG_PACKAGE_luci-app-honk=y
CONFIG_PACKAGE_luci-i18n-honk-zh-cn=y

CONFIG_PACKAGE_kmod-sched-core=y
CONFIG_PACKAGE_kmod-sched-bpf=y
CONFIG_PACKAGE_kmod-veth=y
CONFIG_PACKAGE_kmod-nft-queue=y

CONFIG_PACKAGE_v2ray-geoip=y
CONFIG_PACKAGE_v2ray-geosite=y

CONFIG_PACKAGE_rpcd-mod-ucode=y
CONFIG_PACKAGE_unzip=y
CONFIG_PACKAGE_jsonfilter=y

CONFIG_KERNEL_DEBUG_INFO=y
CONFIG_KERNEL_DEBUG_INFO_BTF=y
# CONFIG_KERNEL_DEBUG_INFO_REDUCED is not set
